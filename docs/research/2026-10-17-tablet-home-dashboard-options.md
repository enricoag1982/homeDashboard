# Research: options for a wall-tablet home dashboard

## Question

What are the options, in October 2026, for a self-built web page on a wall-mounted tablet that shows and controls the household's Alexa (Echo) devices, lights, Sonos speakers and Nest thermostat, and shows Google Calendar, Google Keep and the weather forecast? Is a web page alone enough, or is an always-on computer needed?
The answers feed the open decisions on the integration hub ([ADR-0007](../decisions/0007-choose-the-integration-hub-for-home-devices-and-services.md)), the wall tablet ([ADR-0008](../decisions/0008-choose-the-wall-tablet-and-kiosk-browser.md)) and the implementation language ([ADR-0005](../decisions/0005-choose-primary-implementation-language.md)).

Starting point, as given by the owner:

- A home in the United States.
- Philips Hue with a bridge, plus Wi-Fi bulbs or plugs of unknown brands, some of them set up only in the Alexa app.
- A Google Nest thermostat, generation not yet checked.
- A personal Gmail account, not Google Workspace.
- No always-on computer yet, but open to adding one. The tablet is not chosen yet.

Method: five web research tracks on 2026-10-17 (hub and architecture, Alexa and Sonos, lights and Nest, Google data and weather, tablet and kiosk), then one synthesis, which is this note. The detailed notes of each track are listed under [Sources](#sources).

> [!WARNING]
> Many vendor pages (Google, Amazon, Sonos, Signify, Fully Kiosk and the Home Assistant docs) could not be opened directly from the research environment. Those findings rest on search extracts or on the docs' sources on GitHub, and the detailed notes mark them. Recheck prices, limits and version numbers before relying on them.

## Findings

### Summary

A web page on its own cannot run this dashboard. Browsers block an HTTPS page from calling plain-HTTP devices on the home network, Chrome now makes public sites ask permission before they reach local devices, page JavaScript cannot discover Sonos or Hue on the network, and Google's browser-only sign-in issues no refresh token, so a tablet nobody taps loses Google access as soon as its first token expires. The owner therefore needs **one always-on computer on the home network**. In October 2026 the best use for it is **Home Assistant (HA) as the integration hub, with the owner's own page as its only client**. A Home Assistant Green costs **$199**, double its 2023 launch price because of the 2026 memory-chip shortage. The optional cloud subscription costs **$65 a year**. HA's core integrations already cover Hue, Sonos, Nest, Google Calendar, Google Tasks, National Weather Service (NWS) forecasts and Echo devices, so the page talks to one WebSocket API instead of seven vendors. Two items on the list have no official API. **Echo devices** can be reached only through reverse-engineered Alexa-app APIs that need authenticator-app two-factor login and an occasional re-login. **Google Keep has no API for personal Gmail accounts**; the only route is an unofficial Python library that needs a "master token" with access to the whole Google account. Lights that exist only in the Alexa app need an evening of inventory rather than code. For the wall, the default is a **Samsung Galaxy Tab A11+ (about $161–250) with an 80% charge cap, running Fully Kiosk Browser PLUS (€8.90 one-time)**; Amazon stopped making Fire tablets on 8 October 2026. For the open language decision the consequence is direct: the page is browser code and HA's official client library is TypeScript, so **TypeScript is effectively fixed for the front end**. Java would fit only an optional thin backend, and it has the weakest library support for Sonos and Alexa.

### Browser and vendor rules rule out a page-only dashboard

A static page on the tablet hits the browser's security model before it reaches a single device. Browsers block `fetch` and XHR calls from an HTTPS page to any `http://` address as mixed content; only loopback addresses are exempt ([MDN](https://developer.mozilla.org/Security/MixedContent)). Since **Chrome 142 (28 October 2025)**, a public website must also win a Local Network Access permission prompt before it can call a private IP address. Chrome lifts mixed-content blocking only when it knows in advance that the target is local, such as a private IP literal or a `.local` name ([Chrome for Developers](https://developer.chrome.com/blog/local-network-access); [Dynamsoft](https://www.dynamsoft.com/web-twain/docs/faq/chromium-142-local-network-access-issue.html)). Android WebView, the engine inside Fully Kiosk, was designed to grant that permission without asking, though the evidence is a 2025 design thread rather than shipped documentation ([blink-dev](https://groups.google.com/a/chromium.org/g/blink-dev/c/cwu_RUmBpzY/m/JWenvGViCAAJ)). Even with permission, page JavaScript has no UDP access. It therefore cannot run the SSDP and mDNS discovery that Sonos and Hue rely on ([j2inet](https://j2inet.blog/2018/12/28/ssdp-discovery-in-html/)). Most device APIs also send no CORS headers for arbitrary origins. HA is the exception, with a `cors_allowed_origins` setting ([HA http docs](https://raw.githubusercontent.com/home-assistant/home-assistant.io/current/source/_integrations/http.markdown)). Google closes the last gap. Its browser-only "token model" issues **no refresh token** and needs a user gesture for every new access token. Only the server-side "code model" returns a refresh token that works "without the user being present" ([Google Identity](https://developers.google.com/identity/oauth2/web/guides/use-code-model)).

The vendors add requirements that only a long-running process can meet. The new **Hue Bridge Pro is HTTPS-only and presents certificates from Signify's own certificate authority** on a LAN address, which a browser will not trust. It has also dropped UPnP discovery in favour of mDNS ([homebridge-hue #1219](https://github.com/ebaauw/homebridge-hue/issues/1219)). Nest thermostat changes arrive through a **Google Cloud Pub/Sub subscription** ([HA Nest](https://www.home-assistant.io/integrations/nest/)). Sonos's official cloud API sends events only to a webhook at a **public HTTPS callback URL** ([Sonos docs](https://docs.sonos.com/docs/subscribe)), and Sonos album art comes over plain HTTP from each speaker. Echo control and Google Keep work only through unofficial libraries that run on a server. Each of these needs something that stays on, holds a secret and receives pushes.

Security points the same way. A wall tablet is physically exposed, and an HA long-lived token carries the full permissions of the user who created it ([CodeWords](https://www.codewords.ai/blog/home-assistant-access-token)). If the page talks to a single origin the owner controls, that origin holds every Google, Amazon, Sonos and Nest credential, and the tablet holds one revocable login. Serving the page from that same origin also removes mixed content, CORS and the Local Network Access prompt from the picture. **So an always-on computer is required**, and the real question is what runs on it.

The 2026 memory-chip shortage changed that purchase. **Home Assistant Green**, the plug-and-play box sold by HA's company Nabu Casa, launched at $99 and now costs **$199**; Nabu Casa says its component cost "has nearly doubled" ([Nabu Casa](https://www.nabucasa.com/news/2026-01-08-green-pricing-change/); [Notebookcheck](https://www.notebookcheck.net/Rising-costs-in-the-Smart-Home-The-impact-of-the-chip-and-RAM-shortage.1338441.0.html)). The Home Assistant Yellow is discontinued ([Matter Alpha](https://www.matteralpha.com/explainer/home-assistant-yellow-is-discontinued-here-are-the-alternatives)). A **Raspberry Pi 5 8GB board alone costs about $175** after several price rises since December 2025 ([BGR](https://www.bgr.com/2150106/raspberry-pi-cost-ram-crisis/)). Intel N100/N150 mini PCs swing between $125 and $330 depending on stock ([computingforgeeks](https://computingforgeeks.com/best-mini-pc-home-assistant/)). The Pi has lost its price advantage: a mini PC buys headroom for cameras or local voice, and the Green buys zero setup. On either, run the full **Home Assistant OS** rather than a container. HA's Matter Server app is supported only there, and Sonos push events need the speakers to reach HA directly on TCP 1400, which Docker networking complicates ([HA Matter](https://www.home-assistant.io/integrations/matter/); [HA Sonos](https://www.home-assistant.io/integrations/sonos/)). Nabu Casa's subscription costs **$6.50 a month or $65 a year** ([Nabu Casa pricing](https://www.nabucasa.com/pricing/)) and is optional. It adds remote access and lets Alexa voice control HA devices without port forwarding. It is being renamed **Home Assistant Link** with the December 2026 release, with features unchanged ([Nabu Casa news](https://www.nabucasa.com/news/2026-10-02-cloud-becomes-link/)). The wall tablet itself needs none of it.

### Most services integrate cleanly; Alexa and Keep have no official door

With HA as the hub, every item on the owner's list becomes an HA entity with uniform actions. The difficulty sits entirely in what each vendor allows HA to reach.

| Service | Recommended route | Official API | Updates | Main limit or risk |
| --- | --- | --- | --- | --- |
| Philips Hue | HA Hue integration (local CLIP v2) | Yes, local | Push | Bridge Pro is HTTPS-only with Signify certificates |
| Wi-Fi bulbs and plugs with a brand app | Each brand's HA integration | Varies by brand | Push or poll | TP-Link needs cloud login; Wyze and Sengled are poor bets |
| Lights only in the Alexa app | Matter share into HA, else the brand's integration | Matter yes, routines no | Varies | Amazon-exclusive devices stay stuck |
| Alexa and Echo | HA core Alexa Devices | No, reverse-engineered | 5-minute poll plus push | Authenticator 2FA, re-logins, rate limits |
| Sonos | HA Sonos integration (local UPnP) | Local UPnP is "unsupported"; cloud API is official | Push | UPnP toggle must stay on |
| Nest thermostat | HA Nest (cloud API), Matter, or both | Yes | Push | $5 fee; 1st and 2nd gen Learning are dead |
| Google Calendar | HA Google Calendar or own OAuth client | Yes | Poll | Unpublished OAuth apps expire tokens every 7 days |
| Google Keep | Migrate lists, or unofficial Keep Sync | No | 15-minute poll | Master token grants full account access |
| Weather | NWS plus Open-Meteo, radar tiles from Iowa State | Yes | Poll | NWS 5xx errors; Open-Meteo non-commercial only |

Many vendor pages from Google, Amazon, Sonos and Signify could be read only through search-engine extracts during this research, so the exact numbers below should be rechecked against the live pages at build time.

#### Hue and most Wi-Fi brands already run locally through Home Assistant

Hue is the best-supported local light API the owner has. The square v2 bridge and the 2025 Hue Bridge Pro both expose the local CLIP API v2 with a Server-Sent Events stream, and HA's integration is local push: "V2 Hue bridges (square shape) push state changes to Home Assistant instantly" ([HA Hue](https://www.home-assistant.io/integrations/hue/)). The round v1 bridge is end of life. HA's docs note two practical limits. The Hue API delivers at most **one event per second per device**, which throttles button presses. Changing several lights at once works best through Hue scenes, which reach all the lights together instead of one command per light (same source). The Bridge Pro handles 150+ lights against the old bridge's 50 ([MightyGadget](https://mightygadget.com/philips-hue-bridge-pro-review/)), but it enforces HTTPS and has broken some third-party integrations ([Hueblog](https://hueblog.com/2025/09/04/hue-bridge-pro-almost-all-the-answers-to-the-most-important-questions/)). Routing through HA keeps that problem off the page. Controlling Hue over Matter gives only basic light control, without dynamic scenes ([HA Matter](https://www.home-assistant.io/integrations/matter/)). One open question remains: in 2023 Signify made a Hue account mandatory for the app, and reports at the time said it planned to require one for the API too. No 2025–2026 source confirms that this was enforced on the local API ([Hueblog](https://hueblog.com/2023/09/21/philips-hue-soon-only-usable-with-account-2/); [Born's Tech](https://borncity.com/win/2023/10/05/philips-hue-lights-require-cloud-account-from-2024/)).

The Wi-Fi brands sort into clear tiers. **Shelly** is the friendliest: local push for all four device generations with no cloud required ([HA Shelly](https://www.home-assistant.io/integrations/shelly/)). **LIFX** is controlled over the LAN and polled every 10 seconds ([HA LIFX](https://www.home-assistant.io/integrations/lifx/)). **Govee** has an official LAN API that the owner switches on per device in the Govee app, and HA's "Govee lights local" integration uses it ([HA Govee local](https://www.home-assistant.io/integrations/govee_light_local/)). **TP-Link Kasa and Tapo** devices work locally, but newer ones need the owner's TP-Link cloud username and password, and some firmware also needs a "Third-Party Compatibility" toggle switched on in the app ([HA TP-Link](https://www.home-assistant.io/integrations/tplink/)). **Tuya/Smart Life** white-label devices connect through HA's official cloud integration by QR code. Local control needs per-device keys from a Tuya developer account whose free trial expires after a month ([HA Tuya](https://www.home-assistant.io/integrations/tuya/); [TinyTuya](https://github.com/jasonacox/tinytuya)). **Meross** works locally only through the community `meross_lan` integration ([meross_lan](https://github.com/krahabb/meross_lan)). Two brands are poor long-term bets. **Wyze**'s HA option runs on an unofficial API that "may be cut off at anytime" ([ha-wyzeapi](https://github.com/SecKatie/ha-wyzeapi)). **Sengled** Wi-Fi bulbs lost their Alexa skill on 1 August 2025 after prolonged outages ([PCWorld](https://pcworld.com/article/2864586/amazon-yanks-sengleds-alexa-skill-after-a-series-of-service-outages.html)). Replacing those with Matter or Shelly devices costs less than integrating them.

#### Lights trapped in the Alexa app need an inventory, not code

Neither Alexa integration in HA exposes devices configured in the Alexa app as HA lights; the core Alexa Devices integration offers no light or switch control for Alexa-linked devices ([HA Alexa Devices](https://www.home-assistant.io/integrations/alexa_devices/)). The fix depends on how each device joined Alexa, and the routes rank by robustness. The best is **Matter multi-admin**. If a device joined Alexa through Matter, its settings page in the Alexa app shows "Other Assistants and Apps". That option generates a single-use 11-digit code, which adds the device to HA's Matter network while Alexa keeps controlling it ([Amazon help](https://www.amazon.com/gp/help/customer/display.html?nodeId=T6iLWTtbZygaBJnQhg); [TP-Link FAQ](https://www.tp-link.com/us/support/faq/3573/)). This works because Matter devices support at least five controllers at once ([HA Matter](https://www.home-assistant.io/integrations/matter/)). Next best, for devices linked through a brand's cloud skill (Kasa, Govee, Tuya and similar), is to add the same brand account to HA. Alexa voice keeps working in parallel through the brand's skill. Third, a device can be factory-reset and paired to HA directly. Fourth, HA can trigger Alexa routines. It can do this through Alexa Devices' routine buttons, which use the unofficial API, or by exposing an HA virtual switch to Alexa as a contact sensor that fires a routine. The second method is supported but works one way only: no state comes back to the dashboard ([HA Alexa Smart Home](https://www.home-assistant.io/integrations/alexa.smart_home/)). The last resort is the Node library alexa-remote2's smart-home calls, the most fragile route ([alexa-remote](https://github.com/Apollon77/alexa-remote)). Devices that show no maker skill and no Matter option are probably paired directly to an Echo, and are reachable only through routines or by replacement. That is an inference the research could not confirm. One Thread-specific trap: Echo Thread border routers do not share their network credentials, so a Thread device shared from Alexa might need HA's own Thread border router ([HA community](https://community.home-assistant.io/t/amazon-echo-4gen-matter-devices-thread-border-router/567706)). Newer Amazon Basics plugs are Matter-certified ([CSA listing](https://csa-iot.org/csa_product/amazon-basics-smart-indoor-plug-single-outlet/)).

The inventory itself takes one evening. List the brand skills under Skills & Games in the Alexa app. Open each light's settings and look for a skill name or the Matter option. Read the label on the bulb or plug. Match the router's client list by MAC vendor prefix. Then accept HA's automatic discovery prompts, which recognize many brands by DHCP and zeroconf signatures ([HA Nest manifest](https://github.com/home-assistant/core/blob/dev/homeassistant/components/nest/manifest.json)). Some devices may end up moved wholly into HA. To keep "Alexa, turn on the lamp" working for those, the options are Nabu Casa's subscription; a manual Alexa skill, which needs an Amazon developer account, an AWS Lambda function and HA reachable from the internet on HTTPS port 443 with a trusted certificate; or Emulated Hue, which is local but limited to lights and switches and needs port 80 ([HA Alexa Smart Home](https://www.home-assistant.io/integrations/alexa.smart_home/); [HA Emulated Hue](https://www.home-assistant.io/integrations/emulated_hue/)).

#### Echo control exists only through reverse-engineered APIs

Amazon offers **no official API to control an Echo from outside**. Its developer surfaces all point inward. The Smart Home Skill API, now called "smart home add-ons", sends commands from Alexa to the developer's cloud ([Amazon](https://developer.amazon.com/en-US/docs/alexa/smarthome/understand-the-smart-home-skill-api.html)). The Reminders API reaches only reminders "that it created itself" ([Amazon Reminders](https://developer.amazon.com/en-US/docs/alexa/smapi/alexa-reminders-overview.html)). List skills and the List Management API stopped serving Alexa's shopping and to-do lists on **1 July 2024** ([Amazon deprecated features](https://developer.amazon.com/en-US/docs/alexa/ask-overviews/deprecated-features.html)). Alexa+ reached every US customer on 4 February 2026, free with Prime and $19.99 a month otherwise ([MacRumors](https://www.macrumors.com/2026/02/04/amazon-alexa-plus-prime)). Its developer tools, though, are SDKs for businesses such as OpenTable to plug services into Alexa, not ways in for dashboards ([Amazon developer blog](https://developer.amazon.com/en-US/blogs/alexa/alexa-skills-kit/2025/02/new-alexa-announce-blog)).

The unofficial route has matured. HA's core **Alexa Devices** integration (since 2025.6, rated platinum on HA's quality scale) provides several features: speak and announce entities, a media player, buttons that run Alexa routines, a do-not-disturb switch, sensors for the next alarm, timer and reminder, an event for each voice command, and Alexa's shopping and to-do lists. It polls every five minutes and receives lists, volume and media state by push. It requires an authenticator-app second factor (SMS will not work), hits Amazon rate limits, and cannot play music through its speech markup ([HA Alexa Devices](https://www.home-assistant.io/integrations/alexa_devices/)). Its library shipped three releases between 14 and 15 October 2026 ([PyPI aioamazondevices](https://pypi.org/project/aioamazondevices/)). The older HACS Alexa Media Player is still released often (v5.17.0 on 16 October 2026). Its README warns that "Amazon may cut off access at anytime", and in 2026 users reported lost logins after HA updates, with commenters advising a move to the core integration ([AMP](https://github.com/alandtse/alexa_media_player); [HA community](https://community.home-assistant.io/t/alexa-announcements-broken-after-2026-7-4/1019791)). The dashboard should use Alexa Devices alone, since running both doubles the exposure to rate limits. It should also show an explicit "Alexa disconnected" state and send announcements to Sonos when Alexa is down. Echo speakers cannot join Sonos groups, so the page should show the two systems as separate players.

#### Sonos still allows local control but calls it unsupported

Local control over UPnP on TCP port 1400 still works in October 2026. HA's Sonos integration is local push, and the SoCo library it builds on shipped v0.32.0 on 15 October 2026 ([HA Sonos](https://www.home-assistant.io/integrations/sonos/); [PyPI SoCo](https://pypi.org/project/soco/)). A July 2025 firmware update added two Connection Security toggles. **UPnP** is on by default, and turning it off breaks HA with an HTTP 403 error. **Authentication** is off by default, and when switched on it forces third-party integrations to authenticate. Sonos now describes UPnP as "unsupported" and "no longer actively maintained" ([Sonos support](https://support.sonos.com/en-us/article/adjust-connection-security-settings); [Sonos community](https://en.community.sonos.com/product-updates/a-new-player-update-is-live-6930092)). That is a policy risk, not a current breakage. The newer local API that Sonos's own app uses is undocumented ([Sonos community](https://en.community.sonos.com/advanced-setups-229133/where-is-the-lan-api-documented-6930288)). The official cloud Control API is documented and uses standard OAuth, but it delivers events only to a public HTTPS webhook and publishes no numeric rate limits ([Sonos docs: Control](https://docs.sonos.com/docs/control); [Subscribe](https://docs.sonos.com/docs/subscribe)). That makes it a fallback, not the first choice. Under Option B the fallback costs the page nothing, because HA is already the adapter: if Sonos ever switches UPnP off, the HA side changes and the page's `media_player` entity stays the same. Two practical notes: the owner must leave UPnP on and Authentication off, and album art arrives as plain HTTP from each speaker, so the hub has to proxy it before an HTTPS page can show it.

#### The Nest thermostat's generation decides its route

Check the thermostat's generation first. The 1st- and 2nd-generation Learning Thermostats lost all app, remote and third-party connectivity on **25 October 2025** and now run only their stored schedules ([Google support](https://support.google.com/googlenest/answer/16233096); [9to5Google](https://9to5google.com/2025/04/25/nest-learning-thermostats-1st-2nd-gen/)). No API reaches them.

For the supported models, Google's Smart Device Management (SDM) API is the official cloud route. It costs a **one-time, non-refundable $5** and needs a consumer Google account, since Workspace accounts are rejected. Setup involves a Cloud project with the SDM and Pub/Sub APIs enabled, an OAuth client and a Pub/Sub topic. The OAuth app must be published "In production" or "you will get logged out every 7 days" ([HA Nest](https://www.home-assistant.io/integrations/nest/)). The API provides temperature, humidity, mode, heat and cool setpoints, eco mode, heating or cooling status and the fan timer ([google-nest-sdm traits](https://github.com/allenporter/python-google-nest-sdm/blob/main/google_nest_sdm/traits.py)). Only the active sensor's temperature is reported. The rate limits, about 5 queries per minute or 100 per hour per thermostat, are plenty for one home. They come from a localized copy of Google's limits page ([Device Access limits](https://developers.google.com/nest/device-access/project/limits?hl=ja)). The Nest Thermostat (2020) and the Learning Thermostat (4th gen) also support Matter, while the 3rd-gen Learning and the Thermostat E do not ([Leios guide](https://www.leios.consulting/guides/nest-thermostat-home-assistant/)). Shared into HA over Matter, the thermostat gives local, fee-free control of temperature, setpoints and mode, but users report no fan control, no eco or comfort presets and no room sensors ([HA community](https://community.home-assistant.io/t/nest-gen-4/791667); [HA community](https://community.home-assistant.io/t/nest-thermostat-matter-local-hvac-control/603058)). Both routes can run at once. Google's newer Home APIs are native Android and iOS SDKs, still in beta and gated by app certification, so they do not help a web page ([Google Developers Blog](https://developers.googleblog.com/en/home-apis-enabling-all-developers-to-build-for-the-home/); [iOS release notes](https://developers.home.google.com/apis/ios/release-notes)).

#### Google Calendar is free once the OAuth app is published

A personal Gmail account can use the official Calendar API at no cost, but the OAuth setup has one trap. While an app is in "Testing" status, "authorizations by a test user will expire seven days from the time of consent." The fix is to publish the app "In production" and *not* submit it for verification. Google exempts personal use by fewer than 100 users ([Google Cloud Help](https://support.google.com/cloud/answer/13464323?hl=en)). The costs are a one-time "unverified app" warning at consent and a 100-user cap that "applies over the entire lifetime of the project" ([Google Cloud Help: Unverified apps](https://support.google.com/cloud/answer/7454865?hl=en)). Request the narrowest scopes. `calendar.readonly` is enough to read. To add events from the tablet, `calendar.events.owned` covers calendars the owner owns ([Google OAuth scopes](https://developers.google.com/identity/protocols/oauth2/scopes)). Projects created on or after 1 May 2026 get new per-minute quotas (600 requests per minute per user), and Google plans to bill usage above quota "later in 2026". A dashboard polling once a minute is far below that, but a billing alert is prudent if billing is enabled ([Calendar API usage limits](https://developers.google.com/workspace/calendar/api/guides/quota)). Google also deletes OAuth clients unused for six months, which a polling dashboard never triggers ([Google Developers Blog](https://developers.googleblog.com/en/usability-and-safety-updates-to-google-auth-platform/)). HA's Google Calendar integration follows exactly this setup, and its `create_event` action needs read-write access chosen in the integration options ([HA Google Calendar](https://www.home-assistant.io/integrations/google/)). For family members, share each person's calendar with the owner's account, and one grant reads them all. A calendar shared as free/busy only returns no event details. The no-OAuth alternative is each calendar's "Secret address in iCal format", a read-only bearer URL ([Google Calendar Help](https://support.google.com/calendar/answer/37648?hl=en)). HA's Remote Calendar integration refreshes such URLs only every 24 hours, too slowly for a family dashboard ([HA Remote Calendar](https://www.home-assistant.io/integrations/remote_calendar/)).

#### Google Keep has no consumer API, so plan around it

The official Keep API is an administration tool for Google Workspace. Its features "are only available for Google Workspace customers, and are not available for users with personal Google accounts" ([Google Workspace Updates](https://workspaceupdates.googleblog.com/2021/05/keep-audit-logs-and-api.html); [Keep API overview](https://developers.google.com/keep/api/guides)). The unofficial Python library gkeepapi is maintained (0.17.1, January 2026), but login is its weak point ([PyPI gkeepapi](https://pypi.org/project/gkeepapi/)). Google now rejects password and app-password logins. The working method exchanges a short-lived browser cookie for an Android "master token" ([gpsoauth](https://github.com/simon-weber/gpsoauth)), and gkeepapi's own docs warn that this token has **full access to the account** ([gkeepapi docs](https://github.com/kiwiz/gkeepapi/blob/main/docs/index.rst)). The HACS Google Keep Sync integration builds on it. It polls every 15 minutes, recommends a dedicated Google account, and broke in HA 2025.7 when its pinned dependencies failed to install. Users also reported token-generation trouble in 2026 ([Keep Sync](https://github.com/watkins-matt/home-assistant-google-keep-sync); [HA community](https://community.home-assistant.io/t/google-keep-sync-error-in-2025-7/907319); [HA community](https://community.home-assistant.io/t/trouble-generating-google-keep-sync-token/1022890)). The tension is that Google's own voice assistant writes to Keep. Gemini for Home still adds notes and lists there, despite an August 2026 bug that Google says it has fixed ([9to5Google](https://9to5google.com/2026/08/25/google-home-keep-integration-broken-due-to-bug/); [Android Authority](https://www.androidauthority.com/google-home-gemini-upgrades-september-2026-3706505/)). The supported alternatives all show up in HA as to-do entities. Google Tasks uses the same OAuth client as Calendar, though due dates carry no time of day ([HA Google Tasks](https://www.home-assistant.io/integrations/google_tasks/)). Bring! is a family grocery app with a core HA integration ([HA Bring!](https://www.home-assistant.io/integrations/bring/)). HA's own local to-do list needs no cloud at all. Alexa's shopping list is also available through Alexa Devices, unofficially. If the household keeps Keep, the master token belongs to a dedicated account in a secrets store, and the page should treat the Keep tile as optional.

#### Weather is the easy part, with NWS plus Open-Meteo

The National Weather Service API is free and keyless. It asks only for an identifying User-Agent, and NWS says that will become an API key "in the future" ([NWS API](https://www.weather.gov/documentation/services-web-api)). It provides 12-hour and hourly forecasts per 2.5 km grid cell, observations, and the official alerts that no free commercial API matches, with a guideline of one alert request every 30 seconds at most ([NWS alerts](https://www.weather.gov/documentation/services-web-alerts)). It also has a long record of intermittent HTTP 500 errors on grid forecasts, so cache responses and keep a fallback ([weather-gov discussion](https://github.com/weather-gov/api/discussions/241)). Open-Meteo fills that role. It needs no key, allows non-commercial use under 10,000 calls a day with CC BY 4.0 attribution, and layers NOAA's HRRR model at 15-minute resolution over the US ([Open-Meteo terms](https://open-meteo.com/en/terms); [Open-Meteo HRRR](https://open-meteo.com/en/docs/gfs-api)). The paid or limited options matter less. Pirate Weather allows 10,000 calls a month ([Pirate Weather](https://pirateweather.net/)). Apple's WeatherKit allows 500,000 calls a month with a $99-a-year developer membership ([Apple](https://developer.apple.com/weatherkit/get-started/)). OpenWeatherMap's free 1,000 calls a day require a billing subscription ([OpenWeatherMap](https://openweathermap.org/api/one-call-3)). AccuWeather "currently does not offer a free plan" ([HA alert](https://alerts.home-assistant.io/alerts/accuweather/)). For radar, RainViewer's free API dropped future frames and capped zoom at level 7 on 1 January 2026, which is too coarse for a home view ([RainViewer](https://www.rainviewer.com/api/transition-faq.html)). Iowa State's Mesonet (IEM) NEXRAD tiles and NOAA's time-enabled radar service are keyless, so the page can draw them directly on a Leaflet map ([IEM](https://mesonet.agron.iastate.edu/ogc/); [NOAA](https://mapservices.weather.noaa.gov/eventdriven/rest/services/radar/radar_base_reflectivity_time/ImageServer)). A custom page needs one HA detail: weather entities lost their `forecast` attribute in 2024.3, so the page must call the `weather.get_forecasts` action ([HA 2023.9 release notes](https://www.home-assistant.io/blog/2023/09/06/release-20239/)). The research did not verify whether HA's core NWS integration exposes alerts.

## Options and trade-offs

### Home Assistant should be the hub and the custom page its only client

The four realistic architectures differ mainly in how much integration code the owner writes and how much design freedom that buys.

| Option | What runs on the home computer | Design control | Effort to first working panel | Ongoing maintenance |
| --- | --- | --- | --- | --- |
| A. HA with its own dashboards | HA plus community cards | Medium (cards, YAML, CSS) | Days | Monthly HA updates plus each custom card |
| B. HA as hub, custom page | HA, which also serves the page | Full | Weeks | HA updates plus the owner's code against one API |
| C. Fully custom backend | The owner's own service per vendor | Full | Months | Every upstream API change |
| D. Off-the-shelf display | Vendor device or cloud | Low | Hours | Vendor-driven |

The effort figures are judgments drawn from the research, not measurements.

**Option A** is better than its reputation. The Sections grid view is now the default view, and since 2026.2 an auto-generated "Home" dashboard with summary cards is the default for new installs ([HA blog 2026.2](https://www.home-assistant.io/blog/2026/02/04/release-20262/); [HA docs: views](https://www.home-assistant.io/dashboards/views/)). Community cards installed through HACS turn it into a credible wall panel without code. Mushroom (5.2k GitHub stars) and Bubble Card (4.7k) provide touch-friendly tiles, and kiosk-mode, Wallpanel and browser_mod hide the HA chrome, add a screensaver and drive per-browser popups ([Mushroom](https://github.com/piitaya/lovelace-mushroom); [Bubble Card](https://github.com/Clooos/Bubble-Card); [browser_mod](https://github.com/thomasloven/hass-browser_mod)). The limit is that the design is configured, not written. HA also ships a release on the first Wednesday of every month, each with a breaking-changes section, so every custom card has to keep up ([HA FAQ](https://home-assistant.io/faq/release); [HA 2026.10 changelog](https://www.home-assistant.io/changelogs/core-2026.10/)).

**Option B** is a well-trodden, supported path. HA's own frontend and mobile apps use the same WebSocket API: the client authenticates, then calls `get_states`, `subscribe_events` and `call_service` ([HA WebSocket API](https://raw.githubusercontent.com/home-assistant/developers.home-assistant/master/docs/api/websocket.md)). The official `home-assistant-js-websocket` library is TypeScript with zero dependencies. It handles OAuth login with PKCE, token refresh, reconnection and live entity subscriptions, and HA's own frontend depends on it (version 9.7.1) ([GitHub](https://github.com/home-assistant/home-assistant-js-websocket); [frontend package.json](https://raw.githubusercontent.com/home-assistant/frontend/dev/package.json)). Its README tells browser apps to prefer the login flow over long-lived tokens, which last **10 years** ([HA Auth API](https://raw.githubusercontent.com/home-assistant/developers.home-assistant/master/docs/auth_api.md)). HA publishes no versioning promise for this API, and the `subscribe_entities` command the library uses is undocumented. The real risk is smaller than that sounds, because breaking the core messages would break HA's own UI; the churn comes from individual integrations renaming attributes and actions. Prior art shows the pattern working. HAKit is a React kit with 1.3k stars but no commits since March 2026 ([ha-component-kit](https://github.com/shannonhochkins/ha-component-kit)). Glance is a React 19 add-on, still in beta, that "works great with Fully Kiosk on wall tablets" ([HA community](https://community.home-assistant.io/t/glance-a-polished-fully-editable-react-dashboard-for-home-assistant-runs-as-an-add-on/1012606)). hass-react offers a mock mode for developing without a live HA ([hass-react](https://github.com/dlwiest/hass-react)). Building directly on the official library avoids depending on a single-maintainer UI kit. The price of Option B is rebuilding what HA's dashboards give for free, such as device detail dialogs, media browsing and "unavailable" states. A spec scoped to the household's fixed set of devices keeps that bounded.

**Option C** means re-implementing, for each vendor, OAuth and token storage (Google, Nest, Amazon), LAN discovery and event subscriptions (Hue, Sonos), reconnection and rate limiting. HA already does all of this and keeps it current every month with dedicated libraries such as aiohue, SoCo and google-nest-sdm ([HA Hue manifest](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/hue/manifest.json); [HA Sonos manifest](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/sonos/manifest.json); [HA Nest manifest](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/nest/manifest.json)). It also escapes none of the hard parts, because Echo control would still rely on the same reverse-engineered Alexa API. It makes sense only if writing integration code is itself the hobby.

**Option D** fails on coverage. The Echo Hub lists at $179.99 and often sells for $119.99–129.99, but its customizable dashboard is built from Amazon's own widgets, not a page the owner designs ([Thurrott](https://www.thurrott.com/?p=298199); [Slickdeals](https://slickdeals.net/f/18948961-amazon-echo-hub-8-smart-home-control-panel-with-alexa-early-access-119-99)). The Echo Show 15's widgets mostly come in one fixed size ([TechRadar](https://www.techradar.com/uk/reviews/amazon-echo-show-15)). Google's newest Nest Hub is 2021 hardware ([Tech Advisor](https://www.techadvisor.com/article/3139852/google-home-display-could-be-a-gemini-powered-smart-screen.html)). Homey Pro rose to $449 on 1 June 2026 ([Homey](https://homey.app/en-ca/news/homey-pro-price-update-june-2026/)), and Hubitat's C-8 Pro costs $179.95 ([PromptQuorum](https://www.promptquorum.com/smart-home/best-smart-home-hubs-2027)). DAKboard is a display board whose Pro tier costs $35 a month ([DAKboard](https://dakboard.com/pricing)). MagicMirror² is the closest "design your own page" product, but each device needs a community module ([MagicMirror²](https://github.com/MagicMirrorOrg/MagicMirror)). None of them reads Google Keep.

The recommendation is **Option B, built on top of a working Option A**. First, install HA and add the integrations. Then put together a quick HA tablet view, which serves as a fallback and teaches the entity IDs. Only then specify and build the custom page against the WebSocket API. Serve the page from HA itself (as an add-on or from its `/local/` folder) so that it shares HA's origin, and add a backend-for-frontend (BFF) only when a requirement demands one. Give the tablet a dedicated HA user and log in once through the library's login flow, so the tablet stores a revocable refresh token rather than a 10-year token baked into the page bundle. The research did not establish whether current HA can limit that user to specific entities; HA has historically lacked fine-grained permissions. Up-front cost comes to roughly **$375–465**: Green $199, Tab A11+ $161–250, Fully about $10 and the Nest API's $5 fee, before the mount and any power-over-Ethernet gear.

### A Samsung tablet running Fully Kiosk is the default panel

The tablet market moved this month. On 8 October 2026 Amazon replaced Fire tablets with **Android 16 "Alexa Tablets" that include Google Play**, at $229.99, $329.99 and $499.99, and ended Fire tablet production ([TechCrunch](https://techcrunch.com/2026/10/08/amazon-unveils-new-alexa-tablets-with-alexa-and-google-play-store-access/); [9to5Toys](https://9to5toys.com/2026/10/08/amazon-debuts-all-new-android-alexa-tablets-today/); [Quartz](https://qz.com/amazon-alexa-tablets-fire-lineup-discontinued-100826)). Some outlets cite $549.99 for the 12 Pro. That ends the old default of a cheap Fire HD 10 running Fully Kiosk. Fire OS also froze its built-in browser engine, which caused HA dashboard failures ([HA community](https://community.home-assistant.io/t/fire-hd-10-kiosk-mode-2022/491114)). The Google Pixel Tablet, popular for its dock, was discontinued in September 2026 ([Tech Advisor](https://www.techadvisor.com/article/3232946/farewell-pixel-tablet-i-barely-knew-you.html)).

| Device | US price, Oct 2026 | Charge cap | Kiosk route | Verdict |
| --- | --- | --- | --- | --- |
| Samsung Galaxy Tab A11+ | $249.99 list, $161–229 on sale | 80% "Maximum" mode | Fully Kiosk PLUS with HA integration | Best value |
| Samsung Galaxy Tab S10 FE | $419.99–449.99, $335 on sale | 80% "Maximum" mode | Same | Larger and faster |
| iPad (A16) | $349, seen at $299 | 80%, with occasional full charges | Guided Access, Kiosk Pro, HA app kiosk mode | Best browser, weakest remote control |

| Sonoff NSPanel Pro 120 | $109.90–129.90 | Mains-powered panel (verify per model) | Needs a manual browser-engine update | Secondary room panel only |
| Lenovo tablets | Not found | Automatic 60% that updates re-enable | Fully | Avoid for a wall |

Prices come from [9to5Toys](https://9to5toys.com/2026/06/24/2026-galaxy-tab-prime-day/), [Productchart (A11+)](https://www.productchart.com/tablets/similar_to_50084), [Productchart (S10 FE)](https://www.productchart.com/tablets/similar_to_50991), [iClarified](https://www.iclarified.com/82634/amazon-discounts-new-102inch-ipad-to-299-deal) and [Sonoff](https://sonoff.tech/en-br/collections/central-control-panel). Battery behaviour comes from [Samsung](https://www.samsung.com/au/support/mobile-devices/galaxy-battery-protection-feature-in-one-ui-6-1/), [Apple](https://support.apple.com/en-gb/118418), [Hexnode](https://www.hexnode.com/forums/topic/how-to-disable-battery-protection-mode-on-lenovo-tablets/) and [blakadder](https://blakadder.com/android-panel-webview/). All prices moved during 2026, so recheck them at purchase.

The Samsung route wins on control. Battery protection's "Maximum" mode stops charging at 80% ([Samsung](https://www.samsung.com/au/support/mobile-devices/galaxy-battery-protection-feature-in-one-ui-6-1/)). **Fully Kiosk Browser PLUS** is a one-time **€8.90 plus tax per device**, transferable between devices ([Fully license](https://license.fully-kiosk.com/license/single)). It exposes a password-protected REST API on port 2323 ([SharpTools docs](https://docs.sharptools.io/bridge/integrations/fully-kiosk)). HA's core Fully Kiosk integration, which requires PLUS, adds controls for screen on and off, brightness, screensaver and motion detection, plus battery level and charging state ([HA Fully Kiosk](https://www.home-assistant.io/integrations/fully_kiosk)). Those are exactly the hooks needed for night mode and a smart-plug charging backstop. The open-source WallPanel fork was archived on 5 May 2025 ([WallPanel](https://github.com/TheTimeWalker/wallpanel-android)). FreeKiosk, under the MIT licence, is the open fallback ([FreeKiosk](https://github.com/RushB-fr/freekiosk)). The iPad (A16) has the more polished browser engine and its own 80% cap ([Apple](https://support.apple.com/en-gb/118418)). In iPadOS 26, sites added to the Home Screen open as web apps by default ([WebKit](https://webkit.org/?p=16993)). The Screen Wake Lock API has worked inside Home Screen web apps since iOS 18.4 ([WebKit bug 254545](https://bugs.webkit.org/show_bug.cgi?id=254545); [Progressier](https://progressier.com/pwa-capabilities/screen-wake-lock)). But Guided Access ends on every reboot, and Single App Mode, which survives reboots, needs Apple Configurator or device management ([Virtual Front Desk](https://www.virtualfrontdesk.com/knowledge-base-article/ipad-kiosk-mode-guided-access)). The HA iOS app's kiosk mode, reworked in July 2026, adds screensaver and brightness commands, but it only helps a dashboard running inside the HA app ([Notebookcheck](https://www.notebookcheck.net/Home-Assistant-Neues-Update-erweitert-Kiosk-Modus.1354575.0.html)). A custom page on an iPad gets no remote screen control.

Always-on use has its own failure modes. Battery swelling from constant charging is the main long-term failure, and community reports describe swollen batteries pushing screens off their frames ([HA community](https://community.home-assistant.io/t/tablet-as-wall-panel/734479)). The usual defence has two layers: the built-in 80% cap, plus an HA automation that cycles a smart plug using the battery level Fully reports. These are forum practices, not safety guidance. Choose an LCD rather than an OLED panel for a static layout, and keep the tablet away from sun and heater vents ([AndroidGuys](https://androidguys.com/promoted-news/how-to-turn-a-spare-android-tablet-into-a-wall-dashboard-for-your-home/)). The cleanest flush-mount power is a power-over-Ethernet-to-USB-C adapter that negotiates USB Power Delivery; 5-volt-only splitters may not keep a 10–11 inch tablet charged ([POE Texas](https://reach.dog/shop/poe-texas/products/gat-usbc)). For night mode, an external motion or mmWave presence sensor driving the screen through the Fully integration beats Fully's camera motion detection. Users find the camera "too touchy", triggered by changing light, and it avoids an always-on indoor camera ([HA community](https://community.home-assistant.io/t/ha-on-my-wall/145998); [HA blueprint](https://community.home-assistant.io/t/blueprint-intelligent-wall-tablet-screen-control-on-off-on-motion/1016447)).

The page itself should tolerate any of these devices. It should re-request the wake lock whenever it becomes visible again ([Vaadin](https://origin.vaadin.com/docs/next/flow/browser-apis/wake-lock-api)), leave sound to the speakers because audio needs a user gesture on both engines ([WebKit](https://webkit.org/blog/6784/new-video-policies-for-ios/)), and reconnect its WebSocket automatically. If it uses HTTPS on the LAN, it needs a certificate the tablet trusts. On an iPad, a self-signed certificate must be installed as a profile and manually trusted before Safari allows WebSockets ([code-server docs](https://coder.com/docs/code-server/v3.12.0/ipad)). A real certificate for a domain the owner controls, or Tailscale's, avoids that step. The tablet should stay local-only, with a dedicated low-privilege HA user and a remote-admin password set in Fully. Remote access belongs on the owner's phone, for example through Tailscale with no port forwarding ([Tailscale](https://www.tailscale.com/blog/remotely-access-home-assistant)).

### The page is TypeScript whatever ADR-0005 decides

The open [ADR-0005](../decisions/0005-choose-primary-implementation-language.md) weighs Java, TypeScript and other options and lists "ecosystem maturity for the expected integrations" as a driver. This research answers that driver for this project. The page runs in a browser, so it is TypeScript or JavaScript in any architecture. The HA ecosystem confirms the pull. HA's frontend is TypeScript on Lit web components ([home-assistant/frontend](https://github.com/home-assistant/frontend)), the official WebSocket client is TypeScript, and the custom HA front ends found in the research (HAKit, Glance, hass-react) are React with TypeScript. Even openHAB, the open-source hub written in Java, rebuilt its main UI on Vue 3 and introduced TypeScript in December 2025 ([openHAB 5.1](https://www.openhab.org/blog/2025-12-22-openhab-5-1-release)).

The real choice is about an optional backend. Under Option B no backend is needed at all, which makes this a single-language TypeScript project served from HA. If a requirement later calls for a backend-for-frontend, for example to hold the HA token server-side, merge data, or add an adapter HA lacks, Java with Spring Boot or Quarkus could do the job as a thin proxy. It would add a second language without removing the first, and the research found no maintained Java client for HA's WebSocket API, though it did not search exhaustively. A TypeScript backend on Node instead reuses the official client, which runs in Node with a WebSocket polyfill, and shares types with the page ([home-assistant-js-websocket](https://github.com/home-assistant/home-assistant-js-websocket)). Code added inside HA itself, such as a custom integration, would be Python, because HA core and its device libraries are Python ([home-assistant/core](https://github.com/home-assistant/core)).

If the owner ever left HA (Option C), the library landscape would decide the matter, and Java ranks last:

| Need | Python | Node and TypeScript | Java |
| --- | --- | --- | --- |
| HA client | HA itself | Official home-assistant-js-websocket | None surfaced |
| Google APIs | Official client | googleapis, 12.3k stars, active | google-api-java-client, 1.5k stars, active |
| Hue | aiohue, HA's own | node-hue-api, last npm release a 2023 beta | yetanotherhueapi, 70 stars |
| Sonos | SoCo v0.32.0, October 2026 | node-sonos v1.14.3, February 2026 | sonos-controller, archived since 2020 |
| Echo | aioamazondevices, AlexaPy | alexa-remote2 v8.1.1, August 2026 | None surfaced |
| Keep | gkeepapi | None surfaced | None surfaced |

Sources: [googleapis](https://github.com/googleapis/google-api-nodejs-client), [google-api-java-client](https://github.com/googleapis/google-api-java-client), [aiohue](https://github.com/home-assistant-libs/aiohue), [node-hue-api](https://www.npmjs.com/package/node-hue-api), [yetanotherhueapi](https://github.com/ZeroOne3010/yetanotherhueapi), [SoCo](https://pypi.org/project/soco/), [node-sonos](https://www.npmjs.com/package/sonos), [sonos-controller](https://github.com/vmichalak/sonos-controller), [alexa-remote2](https://www.npmjs.com/package/alexa-remote2), [gkeepapi](https://pypi.org/project/gkeepapi/). For Hue, the community OpenHue OpenAPI specification can generate a client in either language ([openhue-api](https://github.com/openhue/openhue-api)).

The strongest case for Java is the owner's familiarity, its static typing, and Google's actively maintained Java client. openHAB also offers an all-Java hub, with a Hue binding that speaks API v2 ([openHAB Hue binding](https://www.openhab.org/addons/bindings/hue/)). None of that changes the front end, and Java's libraries are thinnest exactly where this list is hardest: Sonos and Alexa. The ADR also notes that the repository's tooling already runs on Node. For this project, the evidence supports accepting **TypeScript on Node**. Java stays a reasonable choice only for a future backend with substantial server logic, and only if the owner accepts maintaining two languages.

## Conclusion

The decision that is costly to reverse here is not the language or the tablet but the integration boundary. Once HA holds every credential and absorbs each vendor's monthly churn, the page becomes a thin, replaceable client and the tablet a replaceable screen. Sonos switching off UPnP or Amazon changing its app backend then becomes an HA update rather than a rewrite. That argues for recording "Home Assistant is the integration hub, and the page talks only to its API" as its own ADR, and closing ADR-0005 for TypeScript in the same pass, because the second decision follows from the first.

The specification should treat vendor fragility as behaviour, not as an implementation detail. The Alexa and Keep tiles need defined "disconnected" states and named fallbacks: Sonos announcements in place of Echo announcements, and a Tasks, Bring! or local list in place of Keep. Both depend on access their vendors have never offered officially and can withdraw at will. The first work items are not code at all. An evening spent inventorying the Alexa-only lights, plus a look at the Nest thermostat's generation, decides whether any hardware must be replaced before a page can control it.

Recommended next steps:

1. Inventory the lights that exist only in the Alexa app, and check the Nest thermostat's generation. Both decide whether any hardware must be replaced.
2. Decide the hub ([ADR-0007](../decisions/0007-choose-the-integration-hub-for-home-devices-and-services.md)), then the implementation language ([ADR-0005](../decisions/0005-choose-primary-implementation-language.md)), which follows from it.
3. Decide what replaces Google Keep for shared lists (Google Tasks, Bring! or Home Assistant's own to-do list), or accept the unofficial route with a dedicated Google account.
4. Choose the wall tablet ([ADR-0008](../decisions/0008-choose-the-wall-tablet-and-kiosk-browser.md)) before buying hardware.
5. Write the first OpenSpec change for the dashboard's first capability, with "disconnected" states for Alexa and lists specified as behavior.
6. Adopt product principles. The candidates below follow from this research.

### Candidate product principles

Not adopted yet: `docs/principles.md` holds the adopted ones. In priority order:

1. **Glanceable first.** What the household checks most (time, weather, today's events) is readable from across the room. Controls come second.
2. **Anyone in the household can use it.** No login, no hidden gestures, large touch targets: a guest can turn the lights on.
3. **Secrets stay off the wall tablet.** Tokens and API keys live on the hub. The wall tablet holds at most one revocable credential, with the least privilege the hub allows.
4. **Local first.** What can work on the home network keeps working when the internet is down. When data is stale or a service fails, the dashboard says so instead of showing old data as current.
5. **Official APIs first, unofficial ones contained.** Prefer supported APIs. Where only an unofficial route exists (Echo control, Google Keep), isolate it so that when it breaks, one part of the dashboard stops working, not the whole page.
6. **Household data stays at home.** The dashboard sends personal data only to the services that hold it already, and none of it is committed to this public repository.
